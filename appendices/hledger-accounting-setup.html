Template: hledger accounting setup#

This page describes a plain-text accounting setup that one conference used and that another team can copy. It serves two needs with one set of files. The first is a living budget, a forecast that converges on actuals as the event unwinds. The second is a shadow double-entry ledger, a record of income and cost that does not depend on the books of whoever signs the contracts, and that produces the figures an accountant needs.

The pattern is general: a plain-text journal, a budget file, import rules for the sales exports, a few canned reports and a smoke test. The 2026 implementation was specific to one ticket platform, one payment provider, one bank and one VAT regime (S104, S105, L-5014). Every journal fragment below is synthetic and every figure is a round placeholder. The decisions about which entity books what, and about VAT, belong in Finance and Legal entity and financial agent, before you set anything up.

When to use it#

  • You want a budget-to-actual view from the day ticket sales begin, not a spreadsheet rebuilt from memory at the end. Tooling kept from the start keeps every earlier commitment visible (L-5044).

  • A financial agent, a company or a university keeps the official books, and the team needs its own factual record next to them.

  • Someone on the team is comfortable with a command line and git. Nobody else needs to be.

If you only need a budget, start with the budget sheet template and skip this page.

Prerequisites#

  • hledger version 1.30 or later. The 2026 setup was tested with 1.50 (S104). The fragments on this page were checked with 1.52.

  • A POSIX shell and awk.

  • git, so two workstations stay in sync.

Layout#

main.journal        top-level file, includes the four below
accounts.journal    decimal mark, commodity, chart of accounts
imported.journal    generated by hledger import, never edited by hand
manual.journal      hand-entered transactions
budget.journal      periodic-transaction budget

rules/              CSV rules files, preprocessing scripts, import state files
bin/                the four canned reports
tests/run-tests.sh  smoke tests
source-data/        exports, invoice PDFs and receipts (keep private)

main.journal holds only include lines:

include accounts.journal
include imported.journal
include manual.journal
include budget.journal

Step 1, declare the chart of accounts#

Declare every account. hledger check accounts then catches a typo before it becomes a second, silent account.

decimal-mark .
commodity 1000.00 EUR

account assets:bank:conference
account assets:bank:payment-provider
account assets:receivable
account assets:prepaid:venue
account assets:prepaid:vat
account liabilities:vat:output
account equity:conference-current
account equity:reserved:contracted
account revenue:tickets
account revenue:sponsors
account expenses:venue
account expenses:catering
account expenses:av
account expenses:print
account expenses:fees:ticketing
account expenses:fees:payment

Keep the top level small: assets, liabilities, equity, revenue, expenses. Add one level per workstream under expenses, so the budget lines and the cost lines match.

Step 2, write the living budget#

The budget is a set of periodic transactions. Virtual postings, written in parentheses, let each budget line stand alone without a balancing entry.

; Ticket income, spread evenly until the target date.
~ monthly from 2027-02-01 to 2027-09-01  ; phase:sales
    (revenue:tickets)        EUR -1000.00

; Venue deposit, one lump in a single month.
~ monthly from 2027-04-01 to 2027-05-01  ; phase:deposit
    (expenses:venue)         EUR 500.00

Compare budget and actuals with the budget report:

hledger -f main.journal balance --budget -E revenue expenses -p 2027-04..2027-06

The report shows each account's actual amount and the percentage of its goal. Update the budget file whenever a decision changes a line. The budget is a living forecast, so the history of changes belongs in git, not in file copies.

Step 3, import the sales exports#

Each export becomes one rules file. A rules file maps the columns of the CSV to postings. The example turns a ticket order into a sale that splits gross, net and VAT.

# rules/ticketing-orders.csv.rules
source ../source-data/orders/orders-*.csv
skip 1
fields date, code, ticket, gross, vat, net
date-format %Y-%m-%d
currency EUR
description Ticket order, %ticket
account1 assets:receivable
amount1 %gross
account2 revenue:tickets
amount2 -%net
account3 liabilities:vat:output
amount3 -%vat

Run the import:

hledger import -f imported.journal rules/ticketing-orders.csv.rules

The command reports how many transactions it imported, or that it found nothing to import. It is idempotent. Platform exports are usually cumulative: each one contains every row since the campaign started. hledger deduplicates through a state file next to the rules file, named .latest.<rules file name>. Commit that state file, so both workstations agree on what has been imported (L-5060).

Two practical points follow from the 2026 experience.

  • Arithmetic that hledger rules cannot do, such as computing net from gross, goes into a small preprocessing script that writes a derived CSV. Keep the original export untouched.

  • An export with a different decimal mark needs a normalizing script before the rules read it. If the amounts land about one hundred times too large or too small, check that script first.

Give every generated transaction a code that points back to the source row, such as an invoice number or a payout identifier. The audit trail then reads hledger -f main.journal register code:INV-0001.

Step 4, keep the manual boundary explicit#

Not everything is imported. The 2026 runbook automated the ticket platform and payment provider imports, and kept bank entry assisted and refunds manual (L-5063). Write down your own boundary the same way. A typical split:

  • Imported: ticket orders and payment provider payouts.

  • Assisted: bank lines. Someone exports them, removes the lines that do not belong to the conference, and reviews each booking.

  • Manual: invoiced sponsors, supplier invoices, costs paid by someone else, grant receipts, refunds, contract signings and VAT clearance.

A manual invoice and its payment look like this. The 21 percent rate is an illustration as of 2026-09 and carries no advice. Use the rules of your own jurisdiction.

2027-04-10 (SP-0001) Sponsor invoice, Example Sponsor A
    assets:receivable          EUR 2420.00
    revenue:sponsors           EUR -2000.00
    liabilities:vat:output     EUR -420.00

2027-04-25 Payment for SP-0001
    assets:bank:conference     EUR 2420.00
    assets:receivable          EUR -2420.00

hledger balance assets:receivable then lists what has been invoiced and not paid.

Step 5, add a committed-spend overlay if you need one#

A strict profit and loss statement looks healthier than the conference is, because a signed venue contract does not appear as a cost until the invoice arrives. The overlay fixes the view without changing the books.

Record the signing against a reserve, net of VAT. Record a prepayment as a prepaid asset plus a prepaid VAT asset, and unwind the reserve by the net part.

2027-03-01 Venue contract signed, net of VAT
    equity:conference-current      EUR 5000.00
    equity:reserved:contracted     EUR -5000.00

2027-04-01 Venue prepayment
    assets:prepaid:venue           EUR 1000.00
    assets:prepaid:vat             EUR 210.00
    assets:bank:conference         EUR -1210.00
    equity:reserved:contracted     EUR 1000.00
    equity:conference-current      EUR -1000.00

The reports then relabel the prepaid asset and the open commitment as committed expenses, with hledger aliases. The journals stay as they are.

hledger -f main.journal incomestatement \
  --alias '/^assets:prepaid:venue$/=expenses:committed:venue' \
  --alias '/^equity:conference-current$/=expenses:committed:contracted'

Keep this overlay report-only and separate from statutory balances and VAT reports (L-5061).

The overlay holds only while equity:conference-current exactly mirrors the contracted reserve. A cost the parent company pays directly, a VAT clearance or a year-end close can all break that. Test the assumption in the smoke test, and retire or redesign the overlay when the test fails (L-5062).

Step 6, add the four canned reports#

Four small scripts in bin/ save everyone from remembering options. Each passes extra arguments through to hledger.

Script

What it shows

bin/pnl-budget

Budget against actuals, including committed spend.

bin/pnl

Profit and loss, including committed spend.

bin/balance

The whole-journal balance for the period, strict.

bin/vat

The VAT accounts for the accountant, strict.

A script is two lines:

#!/bin/sh
exec hledger -f main.journal balance --budget -E revenue expenses \
  --alias '/^assets:prepaid:venue$/=expenses:committed:venue' \
  --alias '/^equity:conference-current$/=expenses:committed:contracted' "$@"

For ad-hoc reconciliation, read the register of the bank account against the real bank statement, and the register of the payment provider account against its dashboard.

Step 7, run the weekly import cycle#

Once or twice a week, while tickets are on sale:

  1. Pull the latest git state, so both workstations start from the same files. Done when git status is clean.

  2. Download fresh exports from the ticket platform and the payment provider into source-data/. Both are cumulative, so each export replaces the last.

  3. Run the import. Done when it reports a count of imported transactions or none.

  4. Book the bank lines that arrived since the last cycle. Done when the bank account register matches the bank statement.

  5. Verify: run the smoke tests and the budget report. Done when the tests print "ok" and the budget view makes sense.

  6. Commit the exports, imported.journal and the import state files, with a message that names the date the import runs through, then push.

If the import finds nothing and you know there are fresh rows, delete the state file for that rules file and run it again. Stable codes prevent duplicates only if you merge carefully; if in doubt, reset imported.journal and import everything. If the payment provider balance does not return to zero after all payouts should have cleared, a payout or a sale is missing from one of the exports. Download both again and re-import.

Step 8, sync two workstations through git#

Two people can run the cycle on alternate weeks. Commit and push at the end of every cycle, and pull at the start of the next. Commit the import state files together with the journal they describe. Never run an import on two workstations in parallel.

Step 9, write smoke tests#

A short shell script catches the failures that matter before the accountant does. It runs after every import.

#!/bin/sh
set -eu
cd "$(dirname "$0")/.."
fail() { echo "FAIL: $1" >&2; exit 1; }

hledger -f main.journal check accounts balanced >/dev/null \
  || fail "journal does not pass checks"

out=$(hledger import --dry-run -f imported.journal rules/ticketing-orders.csv.rules 2>&1 || true)
echo "$out" | grep -q "no new transactions" || fail "import is not idempotent"

sum=$(hledger -f main.journal balance equity:conference-current equity:reserved:contracted -N -O csv |
  awk -F'"' 'NR > 1 { sub(/ EUR/, "", $4); s += $4 } END { printf "%.2f", s }')
[ "$sum" = "0.00" ] || fail "overlay no longer mirrors the contracted reserve ($sum)"

echo "ok"

Add a test that compares a known worked example against its expected balances. Add a test for every assumption you rely on, so a broken assumption fails loudly.

Adapt it to your conference#

  • Replace the rules files for your ticket platform, payment provider and bank. Expect to write a preprocessing script for each export that is not plain CSV.

  • Replace the VAT accounts with the structure your jurisdiction and your financial agent require. Ask the accountant for the report they want, then build the script for it.

  • Replace the budget lines with the lines from your own budget sheet.

  • Rewrite the design notes as public documentation if you want to share your setup. The 2026 design document was private and could not be republished as it stood.

Applies when#

This setup fits a team that has someone comfortable with plain-text tools and a financial agent or accountant who accepts reports built from exports. It does not replace the statutory books of the entity that signs the contracts.

Thin content#

One implementation, one jurisdiction

thin | kind: gap | needs: A second team to adapt the setup to another ticket platform, bank and VAT regime, and to report which steps broke | who-might-know: Treasurers of past conferences; accountants who work with plain-text ledgers

The setup is generalized from one conference. The overlay, the VAT report and the bank step are the parts most tied to that conference's entity and country.
